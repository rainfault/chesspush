# D. Incremental roadmap

Каждый этап заканчивается проверяемой рабочей версией. После уточнения пользователя 28.09.2026 допустима новая основа вместо переноса старых классов. До переключения на неё текущая версия остаётся доступной; данные и нужные сценарии переносятся проверяемо. Первоначальный макет не утверждён, конкретные экраны проектируются отдельно.

## Первый следующий срез

Делать этапы 1–4 небольшими порциями, начиная с выбора основы, конкретного экрана и одного use case. Извлечение из старого кода — возможность, не обязанность. Целевой end-to-end:

1. Открыть существующую партию из Statistics.
2. Перейти к позиции, добавить текст и разметку.
3. Создать Knowledge либо связать с уже существующим.
4. Перезапустить приложение, открыть Knowledge и перейти точно к исходному узлу.
5. Повторить это знание с прежними тремя оценками.

Это закрывает основной цикл независимо от того, какая доля старого кода используется. Самостоятельная разработка Master search, dashboard-аналитики или SRS до этой вертикали откладывается.

## Сохранность данных и совместимость

- Не удалять legacy `games`, `saved_positions`, `position_reviews`, `training_cards` только потому, что они заменены концептуально. Сначала миграция на копии, отчёт по количествам/ID/ссылкам и переключение единственного writer.
- Новые schema migrations версионировать через существующий `storage_meta`; не добавлять ORM только ради миграций.
- Состояния анализа и коллекции не хранить исключительно в QML Loader; существующие тесты восстановления состояния должны остаться зелёными.
- Перенос worker-логики не меняет start index и экспорт частичной ZST-выборки. PGN и SQLite-writing переводить с GUI-thread только там, где это необходимо для текущего сценария.
- Существующую независимую Training Cards страницу не включать как новую базу знаний. Её данные в будущем переводятся в Knowledge + review aspect.
- До расширения импорта отдельно устранить `casefold()` внешнего Lichess ID в fingerprint. Проверить разные ID, отличающиеся регистром, и миграцию существующих ключей; эта проблема обнаружена при обследовании, но не исправляется скрыто вместе с UI.

## Что остаётся за границами

Pattern Matcher, embeddings, распознавание стратегических идей, ML, поиск «идеальных» моделей, полный ChessBase, масштабное engine UI, сложный SRS, индексация всего дампа, plugin framework и отдельный backend-сервер. До конкретного use case для них не создаются заглушки и сервисные интерфейсы.
