# C. Navigation / UI shell

Пересмотрено 28.09.2026 после замечаний пользователя. Первый макет — **не утверждённый интерфейс**. Его подписи, авторская палитра и Unicode-фигуры отклонены. Ниже требования к следующему проектированию; схемы страниц и размеры остаются предварительными.

## Обязательные требования

1. Название **ChessPush**, без точки.
2. Нигде не размещать мелкие поясняющие подписи: о назначении раздела, возможностях приложения, связи страниц, устройстве хранения и т. п. Не заменять их теми же фразами крупным шрифтом. Например, «Корпусы партий · источники и выборки», «От дебюта к конкретным партиям», «Импорт PGN или последних партий с Lichess», «Тёмная нейтральная тема · единые цвета и масштаб интерфейса» в продукт не попадают. Оставлять заголовки, controls, значения и необходимые состояния. Объяснение самого знания, комментарий к шахматной позиции и текст задания — содержимое пользователя, а не поясняющая подпись к UI.
3. **Две темы: light по умолчанию и dark.** Системная тема не должна менять стартовый default; явный выбор пользователя сохраняется. Обе темы — полные визуальные аналоги соответствующих тем Lichess: фон/градиент, поверхности, цвета, типографика, controls, focus/hover/selected/disabled. Не создавать третью авторскую «нейтральную» тему.
4. Стандартная доска Lichess и стандартные SVG-фигуры, как на предоставленном скриншоте. Цель — совпадение внешнего вида и взаимодействия доски 1 в 1 с сайтом; замена фигур символами шрифта не допускается.
5. Каждый экран проектируется отдельно под реальные сценарии и данные. Наличие страницы в концепте не означает принятия её формы, расположения полей или поведения. До реализации конкретизировать состояния, действия, навигацию и критерии проверки этого экрана.

## Общая композиция

Целевой стек — Qt/Python; PySide6 + QML с WebEngineView для доски остаётся предложенным вариантом. Оболочку и controls можно сделать заново: существующий QML не должен ограничивать точность соответствия Lichess. HTML-концепт в задаче не фиксирует ни состав страниц, ни готовую реализацию.

```text
┌──────────────┬─────────────────────────────────────────────────┐
│ ChessPush    │ Раздел / контекст                    Действие   │
│              ├─────────────────────────────────────────────────┤
│ Home         │                                                 │
│ Databases    │         Большая доска         Ходы / варианты    │
│ Statistics   │                             Объяснение          │
│ Knowledge    │                             Связанные знания    │
│ My Games     │                             Примеры             │
│ Training     │                                                 │
│              │         Назад / вперёд / переворот               │
│ Settings     │                                                 │
└──────────────┴─────────────────────────────────────────────────┘
```

Предварительная гипотеза компоновки: sidebar 184–208 px; заголовок без поясняющей подстроки; рабочее пространство без декоративной обводки. Доска квадратная, доминирующая по размеру. Размеры боковых областей и способ открытия списка партий определяются при конкретном проектировании анализа, а не копируются автоматически из первого макета.

При 1280×800 остаются доска и колонка ходов; дополнительные детали уходят в локальные вкладки. В компактном окне sidebar сокращается, под доской появляются ходы/объяснение. Не уменьшать шрифт до нечитаемого ради сохранения всех колонок. Проверять 100%, 125%, 150% DPI, навигацию клавиатурой и масштабирование доски.

## Семь маршрутов

| Route | Наполнение | Перенос существующего сценария |
|---|---|---|
| `home` | Крупные часы; Rapid/Blitz одной строкой; спокойный фон времени суток | Старый Dashboard не возвращать как есть: рейтинг API ещё не реализован |
| `databases` | Локальные вкладки Lichess / Master; фильтры, прогресс, выборка, экспорт | Существующий DatabaseLoader; Master пока явно недоступен |
| `statistics` | Плотная ECO-таблица; строки открывают соответствующие мои партии | Текущая таблица и формула сохраняются; ссылки Knowledge добавляются при наличии данных |
| `knowledge` | Список знаний → выбранное знание: доска, объяснение, варианты, примеры; локальный режим Review | Коллекция Position Lab, затем связанный review |
| `my-games` | Список моих партий → общий анализ; выбор позиции → создать/привязать знание | Режим Games Position Lab; старый MyGamesController не подключать автоматически |
| `training` | Calculation: позиция → кандидаты/вариант → оценка → проверка | Новый сценарий, не переименование старого «вспомнил/не вспомнил» |
| `settings` | Группы Профиль / Мои партии / Источники и хранение / Внешний вид | Текущие настройки + общий импорт; Engine появляется после интеграции движка |

Общий анализ открывает также внешние и мастерские примеры с breadcrumb `Databases → выборка` или `Knowledge → примеры`. Такие партии не попадают в список «Мои» только потому, что открыт тот же компонент. Route анализа может быть вложенным состоянием текущего раздела; дополнительный восьмой пункт sidebar не нужен.

Семь маршрутов — карта продукта, не готовые макеты страниц. Промежуточная рабочая версия не имитирует реализованный функционал. Новая основа может развиваться отдельно, пока действующие сценарии доступны в предыдущей версии. Пометки о статусе дизайна и демонстрационных данных размещаются в документации/сопровождающем сообщении, а не мелкими служебными подписями внутри приложения.

## Состояния и взаимодействие

- Home: часы и реальные Rapid/Blitz, без поясняющих подстрок. Фон времени суток проектируется в пределах выбранной светлой/тёмной темы, не переключает её и не окрашивает всё приложение в самостоятельную палитру. Конкретные фоны и интервалы времени из первого концепта не утверждены. До загрузки рейтингов — `—`; сетевые ошибки и состояние обновления показывать как фактическое состояние соответствующего действия.
- Databases: основные filters всегда видимы; дополнительные раскрываются. Start index остаётся логическим пропуском, прогресс для ZST — неопределённый индикатор + реальные scanned/found. Cancel сохраняет найденную выборку и экспорт по существующему поведению.
- Statistics: кликабельная строка сохраняет ECO/цвет в контексте перехода. Только реальные числа/ссылки; нет фиктивных «типичных ошибок» по результату партии.
- Knowledge: заголовок идеи важнее заголовка партии. Theory/Self-study и категории отделены от пользовательских tags. Примеры списком, с источником и ролью. «Создать знание» и «Привязать» — два понятных действия из анализа.
- Analysis: клавиши ←/→ для ходов, Home/End для начала/конца при фокусе доски/дерева. В текстовом редакторе клавиши не перехватывать. Выбор promotion обязателен, не превращать всегда в ферзя. Возврат сохраняет текущий узел, ориентацию и черновик.
- Review: до раскрытия скрыты body/shapes/эталон, после — прежние три оценки. История относится к Knowledge.
- Calculation: до фиксации варианта и конечной оценки не передавать в UI ответ, категории «тактика», tags, engine score или заголовок, раскрывающий идею. Ввод кандидатов/рассчитанной линии и оценка — самостоятельные шаги. Проверка сравнивает с явно заданным эталоном; альтернативу не объявлять плохой лишь из-за отличия от одной линии.
- Settings: изменение SQLite-пути — явно «применится после перезапуска», пока не сделано корректное переключение соединений. Импорт — отдельная смысловая группа, использующая общий use case.

## Design system

Канонический файл предложения — [design-tokens.json](design-tokens.json). Он пересмотрен: `defaultTheme: light`, две палитры по значениям официальных тем Lichess, ссылки на стандартные board/piece assets. Это исходные reference tokens, а не заявление о готовом визуальном совпадении всех экранов. Точное оформление controls, размеров, типографики и состояний проверяется на конкретном интерфейсе в обеих темах.

Reference — официальные [default/dark](https://github.com/lichess-org/lila/blob/fa6614fcd5bc8afdad24bf341dbc6686afa4208d/ui/lib/css/theme/_theme.default.scss) и [light](https://github.com/lichess-org/lila/blob/fa6614fcd5bc8afdad24bf341dbc6686afa4208d/ui/lib/css/theme/_theme.light.scss) темы, проверенные 28.09.2026. Не снимать приблизительные цвета со сжатого скриншота, когда доступны исходные значения. Скриншот пользователя — дополнительный критерий визуальной сверки.

Единый источник tokens используется QML и Chessground. Существующий `Theme.qml` и controls можно расширить или заменить целиком; aliases нужны только если это упрощает переход. Общие NavItem/PageHeader/buttons/fields должны воспроизводить принятую систему Lichess. Шрифт — Noto Sans, как в reference; размер и начертания проверяются на конкретных controls. «Secondary» может означать цвет фактических metadata, но не разрешает мелкие поясняющие подписи. Ранее предложенные spacing/radii/layout-числа остаются черновыми до сравнения с реальным экраном.

Одинаковые состояния hover/pressed/selected/disabled/focus, видимый keyboard focus. Ошибки содержат текст, не только красный цвет. Цвет стрелок не единственный способ объяснить вариант — остаются текст и список ходов.

## Chessground

Выбран **официальный** [`lichess-org/chessground`](https://github.com/lichess-org/chessground), npm **`@lichess-org/chessground@10.4.0`**, [release v10.4.0](https://github.com/lichess-org/chessground/releases/tag/v10.4.0) от 27.09.2026. Непосредственная проверка npm `latest`, release API и master выполнена 28.09.2026. Старый unscoped пакет `chessground` не использовать. Release фиксируется точной версией и lockfile; `master` нужен для чтения актуального API, не как плавающая runtime-зависимость.

В рабочем приложении bundle JS/CSS локально, без CDN и сети при открытии доски. Node нужен только для сборки web-ресурсов, не для запуска приложения. Сборочный шаг добавляется при интеграции доски, не раньше. В интерактивном эскизе разрешена загрузка закреплённого модуля с CDN; это не проверка offline Qt-интеграции.

### Доска и фигуры: конкретный reference

Стандартная тема **brown**, фигуры **cburnett** из официального `lichess-org/lila`, в обеих темах приложения. Источники: [board theme](https://github.com/lichess-org/lila/blob/fa6614fcd5bc8afdad24bf341dbc6686afa4208d/ui/lib/css/theme/board/_boards.scss), [brown.png](https://github.com/lichess-org/lila/blob/fa6614fcd5bc8afdad24bf341dbc6686afa4208d/public/images/board/brown.png), [cburnett SVG](https://github.com/lichess-org/lila/tree/fa6614fcd5bc8afdad24bf341dbc6686afa4208d/public/piece/cburnett). Использовать оригинальные SVG, не эмуляцию шрифтом или заново нарисованные приближения.

Для приёмки сопоставить с Lichess Analysis Board: плавное следование фигуры за курсором, начало drag, ghost/origin, корректный drop/cancel, движение кликом, легальные поля, последнюю пару полей, анимацию, шах, promotion, переворот и координаты. Правой кнопкой — кружки/стрелки, повторное удаление разметки, цветовые модификаторы и поведение очистки как на сайте. Конкретную конфигурацию брать из проверенной актуальной интеграции Lichess; библиотечные defaults сами по себе не доказывают совпадение.

Все эти проверки относятся к поведению доски. Они не означают реализацию всего сайта или всех engine-возможностей в текущем этапе.

### Граница board bridge

```text
Python → JS: BoardState(session_id, revision, node_id,
                       full_fen, orientation, last_move,
                       legal_destinations, shapes, interactive)
JS → Python: MoveIntent(session_id, revision, from, to, promotion?)
JS → Python: ShapesChanged(session_id, revision, node_id, shapes)
```

Bridge — UI-адаптер, не шахматный сервис. Он не получает SQLite, SettingsStore, файловые пути или API token. Qt WebChannel асинхронен, поэтому устаревшие intents после смены узла/партии отклоняются по session/revision; после ошибки Python присылает авторитетное состояние. Promotion завершается отдельным выбором до записи хода. Shapes из ответа тренировки не передаются до раскрытия.

Официальный API не содержит шахматных правил. Более того, `getFen()` вызывает сериализацию **расстановки фигур**, а не всех шести полей FEN. Полный FEN, очередь хода, права рокировки, en passant, счётчики и move history хранит Python. Нельзя сохранять `ground.getFen()` в БД как полную позицию. Проверено по [api.ts](https://github.com/lichess-org/chessground/blob/master/src/api.ts) и [fen.ts](https://github.com/lichess-org/chessground/blob/master/src/fen.ts).

Один и тот же view/bridge используется для анализа, знания и тренировочного представления с разными возможностями. Не создавать отдельную chess-логику в JavaScript. Существующий QML-board удаляется только после проверки annotation round-trip, click/drag, promotion, ориентации, DPI, offline-запуска и корректного закрытия WebEngine. [Qt WebChannel API](https://doc.qt.io/qt-6/qtwebchannel-javascript.html) документирует связь JS с опубликованным QObject.
